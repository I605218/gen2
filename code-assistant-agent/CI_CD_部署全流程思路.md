# 项目 CI/CD 部署全流程思路说明

本文档用于说明 `code-assistant-agent` 项目从代码提交到测试、构建、发布、部署、回滚的完整 CI/CD 思路。

这份文档关注的是“整体方案设计”和“落地步骤建议”，适合作为课程项目答辩、系统设计说明和后续工程化实施的依据。

---

## 一、CI/CD 的目标

对本项目而言，CI/CD 的核心目标有 4 个：

1. **持续集成（CI）**
   - 每次提交代码后自动检查项目是否还能正常构建
   - 避免前端、后端、配置之间改坏后无法及时发现

2. **持续交付（CD）**
   - 自动生成可部署产物
   - 包括前端静态资源、后端 Jar 包、容器镜像等

3. **持续部署（Deployment）**
   - 在满足条件时，将最新版本自动部署到目标环境
   - 减少手工上传、手工替换文件的错误率

4. **可追踪与可回滚**
   - 每一次上线都能知道对应哪次提交
   - 出问题时能快速回滚到上一个稳定版本

---

## 二、适用于本项目的总体流程

本项目是典型的“前后端分离 + 部署目录独立”的结构，因此 CI/CD 可以按如下流程设计：

```text
开发提交代码
   ↓
代码托管平台触发流水线（GitLab CI / GitHub Actions）
   ↓
代码检查与测试
   ├─ 前端依赖安装、构建检查
   ├─ 后端依赖安装、编译、测试
   └─ 可选：代码规范扫描 / 安全扫描
   ↓
生成构建产物
   ├─ 前端 dist
   ├─ 后端 app.jar
   └─ 可选：Docker 镜像
   ↓
发布制品
   ├─ 上传至制品库 / 镜像仓库
   └─ 标记版本号
   ↓
部署到测试环境
   ├─ 拉取新版本
   ├─ 重启容器
   └─ 健康检查
   ↓
人工确认或自动门禁
   ↓
部署到生产环境
   ↓
监控与回滚机制
```

## 三、本项目的部署对象

### 1. 前端

前端基于 `Vue 3 + Vite`：

- 开发环境通过 `npm run dev` 启动
- 生产环境通过 `npm run build` 生成 `dist` 静态资源
- 最终由 Nginx 提供静态服务

### 2. 后端

后端基于 `Spring Boot`：

- 通过 Maven 构建
- 产物为 Jar 包
- 在部署环境中由 JRE 或 Docker 容器运行

### 3. 部署层

项目已提供：

- `deploy/docker-compose.yml`
- `deploy/nginx.conf`
- `scripts/deploy.sh`

这意味着本项目非常适合采用：

- **CI 阶段产出构建物**
- **CD 阶段使用 Docker Compose 部署**

## 四、建议的环境划分

为了让部署流程更清晰，建议最少区分以下环境：

### 1. 开发环境（Development）

特点：

- 开发者本地运行
- 前端与后端分开启动
- 用于调试功能

### 2. 测试环境（Staging / Test）

特点：

- 自动部署最新通过构建的版本
- 供组内联调、老师演示前预检查
- 接近正式环境配置

### 3. 生产环境（Production）

特点：

- 仅部署稳定版本
- 上线前最好经过人工确认
- 要求可回滚

## 五、CI 阶段应该做什么

CI 的重点是：**验证代码质量与构建结果**。

### 1. 拉取代码

流水线首先从代码仓库获取当前提交版本。

### 2. 后端检查

建议执行：

```bash
cd backend
mvn clean test
```

作用：

- 下载依赖
- 编译代码
- 运行测试
- 尽早发现 Java 编译错误、依赖错误、接口改坏等问题

如果测试阶段过慢，也可以最少执行：

```bash
mvn clean compile
```

### 3. 前端检查

建议执行：

```bash
cd frontend
npm ci
npm run build
```

作用：

- 验证依赖是否完整
- 验证页面是否可打包
- 及时发现模板语法错误、组件脚本错误、白屏问题

### 4. 可选补充

如果后续要继续工程化，可以再加入：

- ESLint / Prettier
- 前端单元测试
- 后端接口测试
- SAST 安全扫描
- 依赖漏洞扫描

## 六、构建产物设计

流水线通过后，需要生成可部署产物。

### 方案 A：直接产出文件

适合课程项目早期：

- 前端产物：`frontend/dist/`
- 后端产物：`backend/target/*.jar`

优点：

- 简单直接
- 易于理解
- 不依赖镜像仓库

缺点：

- 部署时要自己复制文件
- 环境一致性略差

### 方案 B：产出 Docker 镜像

更适合中后期工程化：

- 前端镜像：打包静态资源 + Nginx
- 后端镜像：打包 Jar + JRE

优点：

- 部署环境更统一
- 更适合持续部署
- 更容易回滚

缺点：

- 需要镜像仓库
- 初始配置稍复杂

对于本项目，建议：

- **课程展示阶段可先采用 A**
- **如果要做完整 CI/CD 答辩方案，推荐说明最终目标是 B**

## 七、CD 阶段部署思路

### 1. 测试环境部署

当主分支或测试分支通过 CI 后，可以自动部署到测试环境。

一个典型流程是：

1. 将前端 `dist` 上传到服务器指定目录
2. 将后端 Jar 上传到服务器指定目录
3. 用 `docker-compose` 或脚本重启服务
4. 执行健康检查

例如：

```bash
./scripts/deploy.sh
```

或者在服务器中执行：

```bash
docker compose -f deploy/docker-compose.yml up -d
```

### 2. 生产环境部署

生产环境建议加一个“人工确认”步骤：

- 通过测试环境验证后
- 由负责人点击发布按钮
- 再触发生产部署

这样可以避免每次提交都直接上线。

## 八、健康检查与验收

部署完成后，不能只看“容器是否启动”，还需要做服务验证。

### 后端检查

建议调用：

- `GET /api/ai/test`
- 或其他健康接口

目的：

- 确认后端已启动
- 确认配置文件加载正常
- 确认数据库和 AI 服务可连接

### 前端检查

建议确认：

- 首页是否可访问
- 静态资源是否加载成功
- `/api` 是否能被正确代理到后端

### 联调检查

上线验收建议最少验证：

1. 页面能打开
2. 用户能注册登录
3. Agent 能正常提问
4. 历史记录能加载
5. 退出登录正常

## 九、版本管理与回滚思路

CI/CD 真正可用的关键不是“能部署”，而是“出问题能撤回”。

### 1. 版本标识

建议每次构建产物都带上版本号，例如：

- Git commit SHA
- 时间戳
- Git Tag

例如：

- `frontend:20260419-abc1234`
- `backend:20260419-abc1234`

### 2. 回滚方式

如果是文件部署：

- 保留上一个版本的 `dist` 与 Jar
- 出问题时重新替换回去

如果是镜像部署：

- 重新指定上一个镜像 tag
- 执行 `docker compose up -d`

### 3. 回滚触发条件

常见情况：

- 前端白屏
- 后端启动失败
- 接口联调失败
- 登录功能异常
- AI 核心功能不可用

## 十、适合本项目的 GitLab CI / GitHub Actions 设计思路

虽然当前仓库里还没有正式写 CI 配置文件，但可以按如下思路设计。

### 流水线阶段建议

```text
stages:
  - install
  - test
  - build
  - package
  - deploy_test
  - deploy_prod
```

### 示例职责划分

#### test-backend

- 执行 `mvn clean test`

#### build-frontend

- 执行 `npm ci && npm run build`

#### build-backend

- 执行 `mvn clean package -DskipTests`

#### package-artifacts

- 打包前端 dist 与后端 jar
- 上传为流水线构建产物

#### deploy-test

- 自动部署到测试环境

#### deploy-prod

- 人工触发
- 部署到生产环境

## 十一、部署配置与仓库中现有文件的关系

本项目仓库里已经有若干可直接支撑 CD 的文件：

作用：

作用：

作用：

- 提供部署环境变量模板
- 便于区分测试环境与生产环境

### `scripts/deploy.sh`

作用：

- 作为自动化部署入口脚本
- 可被流水线直接调用

## 十二、本项目推荐的落地顺序

如果要把 CI/CD 作为课程项目的一部分逐步落地，推荐按以下顺序推进：

### 第 1 步：先完成基础 CI

目标：每次提交都能自动检查项目是否还能构建。

至少做到：

- 后端 `mvn clean compile`
- 前端 `npm ci && npm run build`

### 第 2 步：增加构建产物归档

目标：让流水线输出可复用的发布产物。

至少做到：

- 保存前端 `dist`
- 保存后端 Jar

### 第 3 步：接入测试环境自动部署

目标：主分支更新后自动上线到测试环境。

至少做到：

- 上传产物
- 调用部署脚本
- 自动重启服务

### 第 4 步：补充健康检查

目标：不是“部署完成”，而是“部署成功可用”。

至少做到：

- 检查首页
- 检查后端健康接口
- 检查核心功能链路

### 第 5 步：加入生产环境与回滚机制

目标：形成完整工程闭环。

## 十五、结论

对于 `code-assistant-agent` 项目，最合理的 CI/CD 方案是：

- 用 CI 保证前后端代码持续可构建
- 用 CD 产出前端静态资源与后端可执行产物
- 用 Docker Compose + Nginx 实现测试环境和生产环境部署
- 用健康检查、版本号和回滚机制提高上线稳定性

这套方案既适合课程项目展示，也适合作为后续工程化扩展的基础。
