# Code Assistant Agent

一个面向编程学习场景的智能体应用，包含 `Spring Boot` 后端、`Vue 3 + Vite` 前端，以及用于部署的 `Docker Compose + Nginx` 配置。

项目目标不是只提供一个大模型问答接口，而是构建一个适合课程项目演示与后续扩展的完整系统：

- 前端提供可直接使用的编程学习工作台
- 后端负责 AI 调用、Agent 编排、认证、历史记录与工作台聚合能力
- 部署层支持容器化上线与后续 CI/CD 接入

---

## 三、课程要求对应实现说明

本节用于对应课程中提出的 Agent 基本要求与加分项，说明本项目如何逐条落地实现。

### 1. 基本需求点一：Agent 需要展现出规划和思考能力，而不是简单预定义 workflow

本项目没有把 Agent 设计成“收到请求后直接把 prompt 发给模型，再把结果返回”的单层调用，而是把整个推理过程拆分为多个显式阶段，并将这些阶段组织为可追踪的执行链路。

#### 实现思路

Agent 执行主流程被拆成以下阶段：

1. `planning`
   - 先根据任务类型构建计划步骤
   - 明确本轮目标、执行重点和框架分工
2. `action`
   - 根据任务类型选择可用工具
   - 调用工具补充外部观察信息
3. `reflection`
   - 对当前结果进行反思
   - 判断是否需要二次修正
4. `replanning`
   - 如果反思结果判定当前答案仍不足，则追加补强步骤
5. `answer_generation`
   - 综合计划、工具结果、反思结果生成最终回答

#### 为什么这不是简单 workflow

虽然本项目仍然是工程化实现，不是无限开放式自治 Agent，但它并不是固定写死的线性模板。它具备以下“动态性”：

- 不同任务类型会生成不同计划目标
- 是否调用工具取决于任务类型匹配结果
- 是否触发二次修正取决于工具结果与 reflexion 判断
- 如果工具观察不足，会触发重规划并调整回答策略

#### 具体落地方式

在 Agent 执行过程中，会动态构建：

- `planSteps`：记录当前计划步骤
- `reasoningSteps`：记录推理摘要
- `actionTraces`：记录 Thought / Action / Observation
- `reflection`：记录反思结论
- `stageTraces`：记录每个阶段的执行情况
- `memory`：记录执行过程中的关键上下文记忆

因此，本项目已经能够清晰体现“规划—行动—反思—重规划—输出”的多阶段推理结构。

### 2. 基本需求点二：Agent 需要具备与外部世界交互的能力，至少设计实现 2 个主题相关的外部工具

本项目围绕“编程学习与代码辅助”这一主题实现了 3 个工具，分别服务于报错解释、代码审查、算法讲解与学习路径推荐等场景。

当前工具包括：

1. `ErrorKeywordTool`
2. `CodeComplexityTool`
3. `LearningResourceTool`

虽然这些工具目前主要是面向代码学习场景的领域工具，而不是联网搜索型工具，但它们都参与了 Agent 在推理阶段的“行动—观察”闭环，是当前系统的外部工具能力基础。

#### 工具总体接入方式

Agent 在 `action` 阶段会根据任务类型筛选可用工具，并执行最多 2 个工具。执行完成后，工具输出会进入：

- `toolResults`
- `actionTraces`
- `tools`
- `execution.memory`

也就是说，工具结果不是孤立存在，而是被纳入后续回答生成与反思判断。

---

#### 2.1 ErrorKeywordTool：错误关键词分析工具

**适用任务类型**

- `ERROR_EXPLANATION`
- `CODE_REVIEW`

**工具目标**

当用户问题中包含报错关键词、异常描述、错误上下文时，该工具优先帮助 Agent 做第一轮错误模式归因。

**为什么它属于主题相关工具**

本项目主题是编程学习与代码辅助。对于初学者而言，“看不懂错误信息”是最高频场景之一，因此错误关键词分析工具直接服务于核心主题。

**采用的推理框架**

- 主要参与 `ReAct-style`
- 与 `Plan-and-Execute` 协同工作
- 在 `Reflexion` 阶段作为反思依据之一

**详细推理过程**

1. `Plan-and-Execute` 阶段先生成计划
   - Agent 判断当前任务是报错解释还是代码审查
   - 计划中会加入“结合代码上下文与报错信息进行归因”的步骤
2. `ReAct-style` 阶段决定行动
   - Agent 判断当前需要“补充外部观察来增强结论可信度”
   - 选择调用 `ErrorKeywordTool`
3. 工具执行
   - 读取 `errorMessage`，若为空则退回读取 `question`
   - 对文本进行归一化处理
   - 检测是否命中常见错误模式，例如：
     - 空指针
     - 越界
     - 语法错误
   - 输出一个面向教学的诊断摘要
4. `Observation` 阶段记录结果
   - 工具输出进入 `actionTraces`
   - 同时进入 `tools` 列表供前端展示
5. `Reflexion` 阶段利用该观察结果
   - 如果工具命中较明确的错误模式，Agent 会更有信心组织修复建议
   - 如果未命中特定模式，反思阶段会倾向于提示“需要更多上下文”
6. 回答生成阶段融合工具观察
   - 在最终回答中将工具观察转化为：
     - 根因分析
     - 排查顺序
     - 修复建议
     - 示例代码

**它解决了什么问题**

- 把抽象报错文本转成结构化观察信息
- 降低大模型直接从长问题中抓取错误模式的难度
- 增强报错解释场景下的稳定性与教学性

---

#### 2.2 CodeComplexityTool：代码复杂度分析工具

**适用任务类型**

- `CODE_REVIEW`
- `ALGORITHM_GUIDE`

**工具目标**

对用户输入的代码做基础静态分析，提取行数、循环数量等结构信息，用于辅助 Agent 判断复杂度、可读性与优化空间。

**为什么它属于主题相关工具**

该工具直接服务于“代码优化、代码审查、算法讲解”三个核心学习场景，能够帮助 Agent 给出更具有依据的复杂度分析建议。

**采用的推理框架**

- 主要参与 `ReAct-style`
- 与 `Plan-and-Execute` 深度协同
- 可在 `Reflexion` 阶段作为重规划依据

**详细推理过程**

1. `Plan-and-Execute` 阶段规划目标
   - 如果任务是 `CODE_REVIEW`，Agent 的目标是识别代码缺陷、复杂度与可改进点
   - 如果任务是 `ALGORITHM_GUIDE`，Agent 的目标是抽取题目思路、复杂度和伪代码
2. `ReAct-style` 阶段决定是否调用工具
   - 如果用户提供了代码，且任务和复杂度分析相关，Agent 选择调用 `CodeComplexityTool`
3. 工具执行
   - 读取 `request.code`
   - 统计代码行数
   - 统计循环语句数量
   - 给出“若存在多层循环，需关注时间复杂度和可读性”的结构化摘要
4. `Observation` 阶段记录结果
   - 工具输出被记录到 `toolResults`
   - 同时被转成 `actionTraces` 中的 Observation
5. `Reflexion` 阶段利用该观察
   - 若工具观察较弱或代码信息不足，反思阶段会提示采用保守解释策略
   - 若工具发现循环较多，回答会更倾向于强调复杂度、可读性和优化建议
6. 回答生成阶段融合观察
   - 在 `CODE_REVIEW` 中，工具结果可支持：
     - 复杂度分析
     - 重复循环提醒
     - 可读性建议
   - 在 `ALGORITHM_GUIDE` 中，工具结果可支持：
     - 时间复杂度讨论
     - 步骤解释
     - 实现方式比较

**它解决了什么问题**

- 让复杂度分析不完全依赖大模型自由发挥
- 给代码优化建议增加一层结构性依据
- 在算法讲解中增强对代码实现层面的解释能力

#### 2.3 LearningResourceTool：学习资源推荐工具

**适用任务类型**

- `ALGORITHM_GUIDE`
- `PRACTICE_GENERATION`
- `GENERAL_CHAT`

**工具目标**

根据用户的问题或知识点，为 Agent 提供一个面向学习路径的外部观察结果，使回答不仅停留在“解释这个知识点”，还能够延展到“下一步怎么学”。

**为什么它属于主题相关工具**

本项目的定位不是通用聊天，而是“编程学习工作台”。因此学习资源与学习路径推荐不是附属能力，而是主题核心的一部分。

**采用的推理框架**

- 主要参与 `ReAct-style`
- 在 `Plan-and-Execute` 中承担“补充学习路径”的角色
- 在 `Reflexion` 阶段可用于补强答案的教学性与延展性

**详细推理过程**

1. `Plan-and-Execute` 阶段确定目标
   - 当任务是算法讲解、练习生成或通用问答时，Agent 不只要回答当前问题，还要考虑如何帮助用户继续学习
2. `ReAct-style` 阶段决定调用工具
   - Agent 识别到当前任务适合补充资源与学习路径时，调用 `LearningResourceTool`
3. 工具执行
   - 优先读取 `knowledgePoint`
   - 若为空，则使用 `question`
   - 输出结构化学习路径摘要，例如：
     - 查阅官方文档或教程
     - 搜索基础例题
     - 用最小样例验证理解
     - 记录易错点并复盘
4. `Observation` 阶段记录结果
   - 工具结果写入 `toolResults`
   - 同时进入 `actionTraces`
5. `Reflexion` 阶段补强答案
   - 如果当前回答太偏“知识解释”，反思阶段会提示补足“如何继续学习”的内容
6. 回答生成阶段融合结果
   - 在算法讲解中，加入学习建议与练习方向
   - 在练习生成中，帮助设计从基础到进阶的路径
   - 在通用问答中，提高答案的教学延展性

**它解决了什么问题**

- 避免回答只停留在“当前这一题”
- 让 Agent 更贴近学习助手而非单轮问答机器人
- 增强课程项目中的“教育场景”特征

---

#### 2.4 工具与推理框架的整体协同关系

这 3 个工具并不是孤立被调用的，而是作为 Agent 多框架协同中的“行动模块”存在：

- `Plan-and-Execute`
  - 决定当前任务需要什么样的观察信息
- `ReAct-style`
  - 真正执行工具调用，产生 Observation
- `Reflexion`
  - 根据工具结果判断当前答案是否充分，是否需要补强

因此，本项目在“外部工具能力”上不是简单地做了几个工具类，而是把它们嵌入到了完整的推理闭环中。

### 3. 基本需求点三：Agent 需要具备自我修正能力，能够捕获系统中的异常并处理

本项目在这一点上实现了两个层次的能力：

1. **Agent 层的自我修正能力**
2. **系统层的异常捕获与处理能力**

#### 3.1 Agent 层的自我修正能力

Agent 在执行过程中，会进入显式的 `reflection` 阶段。该阶段会：

- 总结本轮工具观察是否充分
- 判断当前答案是否需要补强
- 若需要，则触发 `replanning`
- 在回答生成后可进一步进入 `refineAnswer`

具体来说，系统会根据以下条件决定是否触发二次修正：

- 用户是否显式开启 `enableReflexion`
- 当前是否没有拿到工具观察结果
- 当前反思内容中是否提示需要“重规划”或“进一步补强”

#### 3.2 自我修正的执行方式

当 reflexion 被触发后，系统会做以下事情：

1. 记录 `retryCount`
2. 重建计划步骤
3. 重建推理摘要
4. 将重规划理由写入 `memory`
5. 再次调用模型生成更完善的答案

因此，这不是简单地“如果失败就再试一次”，而是带有反思依据的“重规划式修正”。

#### 3.3 系统层异常处理

除了 Agent 层的反思修正之外，后端还对系统运行时异常做了统一处理，包括：

- AI 请求繁忙
- AI 接口调用失败
- 认证异常
- 全局异常处理

这部分保证了系统在发生异常时不会直接崩溃，而是能向前端返回受控错误信息。

#### 3.4 当前实现程度说明

当前实现已经满足课程要求中的“具备自我修正能力并能处理异常”的基本目标，但仍偏向课程项目中的“基础可解释版本”。如果后续继续工程化，可进一步扩展：

- 工具失败后的自动替代策略
- 多轮重试策略
- 熔断与降级
- 更细粒度异常分类与监控告警

### 4. 基本需求点四：Agent 需要可视化内部状态流转情况（CLI、Web 等均可）

本项目已经通过 Web 工作台实现了 Agent 内部状态流转的可视化，且不仅是展示最终答案，而是把执行过程中多个层次的状态都组织成结构化数据。

#### 4.1 当前已经实现的内部状态可视化内容

目前后端在 `AgentResponse` 中返回了以下可视化字段：

- `frameworks`
  - 当前执行中启用的推理框架列表
- `execution`
  - 执行元信息汇总
- `planSteps`
  - 计划步骤
- `reasoningSteps`
  - 推理摘要
- `actionTraces`
  - 行动轨迹（Thought / Action / Observation）
- `tools`
  - 工具调用轨迹
- `reflection`
  - 反思结果
- `answer`
  - 最终回答

#### 4.2 execution 元信息中的可视化内容

`execution` 中进一步包含：

- `executionId`
  - 本次执行的唯一标识
- `planStepCount`
  - 计划步骤数量
- `toolCallCount`
  - 工具调用次数
- `actionTraceCount`
  - 行动轨迹条数
- `reflexionTriggered`
  - 是否触发了 reflexion
- `retryCount`
  - 重试 / 重规划次数
- `totalDurationMs`
  - 总执行耗时
- `memory`
  - 关键记忆项
- `stageTraces`
  - 分阶段执行轨迹

#### 4.3 分阶段状态流转可视化

当前系统已经把执行链路拆分成可视化阶段，包括：

- `planning`
- `action`
- `reflection`
- `replanning`
- `answer_generation`

每个阶段都会记录：

- `stage`：阶段名称
- `framework`：所属推理框架
- `status`：阶段状态
- `attempt`：当前尝试次数
- `durationMs`：阶段耗时
- `summary`：阶段摘要

这意味着前端不仅能显示“当前在做什么”，还可以显示“用了什么框架、花了多久、结果怎样”。

#### 4.4 记忆与推理过程可视化

当前系统还实现了以下层面的内部可视化：

##### 1）计划层可视化

通过 `planSteps` 展示：

- 当前计划一共几步
- 每一步要解决什么目标
- 该步骤主要由哪一种框架承担
- 当前步骤状态

##### 2）推理摘要可视化

通过 `reasoningSteps` 展示：

- 当前识别出的任务类型
- 用户问题摘要
- 是否接收了代码上下文
- 是否接收了错误信息
- 是否显式启用了 reflexion

##### 3）行动轨迹可视化

通过 `actionTraces` 展示：

- Thought：为什么做这一步
- Action：执行了什么动作
- Observation：观察到了什么结果

这是当前系统最接近 ReAct 风格解释链路的部分。

##### 4）工具调用可视化

通过 `tools` 展示：

- 调用了哪个工具
- 工具输入是什么
- 工具输出是什么

##### 5）反思结果可视化

通过 `reflection` 与 `execution.reflexionTriggered` 展示：

- 本轮是否进行了自我检查
- 是否认为当前答案还需要补强
- 是否进入了二次修正或重规划

##### 6）执行记忆可视化

通过 `memory` 展示：

- 当前任务类型
- 用户问题摘要
- 初始计划步数
- 工具观察数量
- reflexion 判定结果
- retry 原因
- 最终答案是否已生成

#### 4.5 前端工作台中的可视化承载方式

当前 Web 工作台已经实现以下几类可视化承载：

- 最终回答展示区
- 历史记录侧栏
- 会话状态区
- 仪表盘统计区

结合后端已返回的结构化执行数据，本项目已经具备进一步把“计划步骤、行动轨迹、阶段耗时、工具调用链”做成完整流程面板的基础。

也就是说，当前系统已经实现了“内部状态可输出、可前端承载、可继续扩展”的可视化能力。

---

### 5. 加分项：Agent 有机结合不止一种推理框架，如 ReAct、Plan-and-Execute、Reflexion 等

这一点是本项目的一个核心亮点。

当前 Agent 不是单一框架，而是明确采用了三种推理框架的混合设计：

1. `Plan-and-Execute`
2. `ReAct-style`
3. `Reflexion`

#### 5.1 Plan-and-Execute 的作用

- 负责先规划再执行
- 根据任务类型生成不同目标步骤
- 为后续工具调用和回答生成提供结构化计划基础

#### 5.2 ReAct-style 的作用

- 负责在执行阶段选择工具
- 生成 Thought / Action / Observation 轨迹
- 把“行动”和“观察”引入问答流程中

#### 5.3 Reflexion 的作用

- 负责对当前结果做自检
- 判断是否需要补强
- 在必要时触发重规划和二次修正

#### 5.4 为什么说是“有机结合”而不是简单并列

本项目不是把三种框架做成三个互相独立的模块，而是把它们安排在同一条执行链路中：

- 先由 `Plan-and-Execute` 规划目标
- 再由 `ReAct-style` 选择行动并获取观察
- 然后由 `Reflexion` 决定是否补强
- 若需要，再回到计划层做重规划

因此，这种设计体现的是“框架协同”而非“框架堆砌”。

## 五、当前核心接口

### 1. AI 连接测试接口

- `GET /api/ai/test`

用于测试当前 AI 服务配置是否可用。

### 2. AI 通用聊天接口

- `POST /api/ai/chat`

直接调用底层模型，不经过 Agent 编排。

### 3. Agent 执行接口（结构化输入）

- `POST /api/agent/execute`

适合在结构化模式下调用，显式传入任务类型、语言、错误信息、知识点等参数。

### 4. Agent 自动解析执行接口（自然语言输入）

- `POST /api/agent/auto-execute`

适合真实用户输入，由系统先解析请求，再交给 Agent 执行。

### 5. 工作台接口

- `GET /api/workspace/dashboard`
- `POST /api/workspace/history`
- `GET /api/workspace/session-state`

分别用于：

- 获取工作台概览数据
- 获取历史记录
- 获取当前会话状态

### 6. 认证接口

- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/auth/me`
- `POST /api/auth/profile`
- `POST /api/auth/change-password`
- `POST /api/auth/logout`

分别用于：

- 注册
- 登录
- 获取当前登录用户
- 修改昵称
- 修改密码
- 登出

## 七、数据库与数据归属

当前系统中，历史记录支持游客态和登录态隔离。

### 游客态

- 使用 `sessionId` 区分不同游客会话
- 历史记录仅归属于当前会话

### 登录态

- 历史记录归属于当前登录用户
- 登录 / 退出时会切换前端 `sessionId`
- 避免游客历史与账号历史混淆

主要表包括：

- `app_user`
- `user_session`
- `agent_conversation_history`

初始化 SQL 可参考：

- `backend/src/main/resources/schema.sql`

## 八、本地开发启动方式

### 1. 启动后端

进入后端目录：

```bash
cd backend
```

准备配置：

- 复制 `.env.example` 或按 `application.yml` 配置数据库与 AI 参数
- 确保 MySQL 可用

编译并启动：

```bash
mvn clean spring-boot:run
```

默认后端端口：

- `8080`

### 2. 启动前端

进入前端目录：

```bash
cd frontend
```

安装依赖：

```bash
npm install
```

启动开发服务器：

```bash
npm run dev
```

构建生产包：

```bash
npm run build
```

### 3. 前后端联调

默认情况下：

- 前端通过 Vite 开发服务运行
- 前端调用后端 `/api/...` 接口
- 可通过 `vite.config.js` 或部署层 Nginx 做代理转发
